# Industrial Sensor Data Pipeline

A production-grade data pipeline for an industrial CO₂ capture unit. Fetches time-series sensor data from a REST API, cleans it, detects process cycles, calculates KPIs, and exports results for analysis.

Built as a solo project to replace a fragile legacy pipeline of ad hoc scripts.

---

## Stack

- **Python 3.12** + **uv** for dependency management
- **Polars** for all dataframe operations
- **DuckDB** for KPI output and querying
- **Parquet** (zstd) for raw and cleaned data storage
- **Dagster** for orchestration, scheduling, and data quality checks
- **WinSW** for running Dagster as a Windows service
- **pytest** for testing (242 tests)
- **GitHub Actions** for CI

---

## Architecture

### Data layers

```
raw/        — exact API output, never modified after writing
cleaned/    — derived columns added (phase, cycle_id, cycle_status)
outputs/    — kpis.duckdb, rebuilt from cleaned layer on demand
exports/    — timestamped CSV exports for stakeholders
```

Raw and cleaned layers are partitioned by `unit/year/month/date.parquet`. All writes are atomic (temp file + rename) so a crashed run leaves no partial files behind.

### Pipeline stages

```
preflight → raw_data → cleaned_data → kpi_results
```

Each stage is a Dagster asset. Dependencies are declared explicitly — Dagster enforces execution order and blocks downstream assets on failure.

| Stage | What it does |
|---|---|
| `preflight` | Checks env vars, directory permissions, API auth, UUID reachability |
| `raw_data` | Fetches sensor data from REST API → raw Parquet |
| `cleaned_data` | Parses timestamps, assigns phase labels and cycle IDs → cleaned Parquet |
| `kpi_results` | Calculates per-cycle KPIs → DuckDB |

---

## Orchestration (Dagster)

The pipeline runs on a weekly cron schedule via Dagster's scheduler. Dagster runs as a persistent Windows service (WinSW), starting automatically on boot.

**Asset checks** run after each materialisation and appear as pass/fail in the Dagster UI:
- Raw files exist and are non-empty
- Raw files match the expected schema
- Cleaned files contain required derived columns
- At least one process cycle was detected

**Performance monitoring** — each asset logs elapsed time and memory usage (RSS delta) via `psutil` to the Dagster run log. Run history is queryable via the UI for performance comparison across code changes.

---

## Error handling

Every failure mode raises explicitly. Failures are collected and reported together before raising so all issues are visible at once rather than one at a time.

- **Pre-flight**: missing env vars, unwritable directories, auth failure, UUID not found in API response
- **Fetch**: authentication failure, empty API response, schema validation failure (missing expected columns), write errors
- **Clean**: raw file not found, read/write errors, cycle summary not written
- **KPI**: cycle summary missing or empty, DuckDB not written

Unexpected schema columns are logged to a drift log and dropped rather than failing — the pipeline degrades gracefully on new sensors but fails hard on missing ones.

---

## Parallelisation

The fetch stage submits all unit/date combinations concurrently via `ThreadPoolExecutor`. This is implemented in the underlying `fetch_all()` function and called from the Dagster asset. The clean and KPI stages are sequential — Polars operations are internally vectorised and the bottleneck is I/O.

---

## Domain logic

The physical process runs in discrete cycles, each consisting of six sequential phases: adsorption, evacuation, heating, desorption, cooling, ventilation. Each phase maps to a step number range from the process controller.

**Cycle detection** is based on step resets: when the step value drops below the previous value and re-enters the adsorption range, a new cycle begins. Each adsorption module (AM) is processed independently.

**KPIs** calculated per cycle per AM include phase durations, electrical and thermal energy consumption, CO₂ mass flow, energy intensity (kWh/tonne CO₂), and sensor means per phase.

## CI

GitHub Actions runs the full test suite on every push. The workflow installs dependencies via `uv`, generates synthetic test data, and runs pytest. Environment variables required by the config are injected as dummy values in the workflow — the test suite mocks all HTTP calls and uses local synthetic data only.

---

## Testing

242 tests across five suites covering config invariants, fetch logic (path helpers, time chunking, schema validation, idempotence), cleaning (phase labelling, cycle detection, status assignment), KPI arithmetic, and run metrics. Integration tests use synthetic Parquet files generated by a dedicated script to avoid any dependency on real API access.

## Key design decisions

- **Single config** — all paths, schemas, phase ranges, and column groupings defined in one place. Nothing else in the codebase hardcodes these.
- **Atomic writes** — all Parquet files written to `.tmp` first, then renamed. Safe on Windows.
- **Schema validation at ingest** — unexpected columns logged and dropped; missing expected columns cause a hard failure before any file is written.
- **`cycle_summary.parquet`** — a single flat manifest of all detected cycles with their status (`complete` / `incomplete` / `error`). Used by the KPI stage to filter and by the orchestrator to detect what needs processing.
- **Dagster over custom orchestrator** — replaced a hand-rolled `run_all.py` + Task Scheduler setup. Gained scheduling reliability, run history, asset-level failure isolation, and data quality checks with minimal added complexity.
